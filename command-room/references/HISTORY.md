# Command Room — failure ledger (bug & incident history)

Narrative context moved out of SKILL.md files (P3.9 bug-archaeology extraction; extends the A7
diet). **Rules live in the SKILL.md files; stories live here.** A behavioral rule (MUST / NEVER /
FORBIDDEN / HARD gate) is never satisfied by an entry here — the skill keeps the rule plus a
breadcrumb like `(Bug #86 — see references/HISTORY.md)`. Per-skill ledgers
(`skills/workspace-manager/references/HISTORY.md`, `skills/workspace-ingest/references/HISTORY.md`)
remain valid; this file is the plugin-wide index and the home for every skill without its own
ledger. Entries are keyed by bug number or incident name. Append-only — archive, never delete.

Note on numbering: bug numbers were assigned per-session in early tracking, so a number can name
more than one incident (e.g. two distinct Bug #82s). Entries below disambiguate in the title.

## Bug #82 — vocative routing miss (v3.13.8.4)
**Symptom:** Addressing the AI by its custom name ("Penelope, what's going on") fell to whichever specialist's substring trigger happened to match — usually nothing — instead of routing into Command Room. **Root cause:** Naming the Brain gave the router no signal; skill descriptions are static at install time, so a custom `brain_name` could never be a positive trigger phrase. **Fix:** A MUST-language gate resolves `workspace.brain_name` first on every turn, strips the wake-word, and re-dispatches the remainder through normal trigger matching. **Rule it produced:** [workspace-manager] "MUST-language gate — brain-name vocative routing".

## Bug #82 — new-project routing miss (v3.13.8.4)
**Symptom:** A bare "new project" followed by a paste of context in the same/next turn didn't match the inline-name trigger `new project [Name]`, so the turn went freeform and the project was never created. M: "a lot of times it doesn't build a new command room project until I say 'new project in command room'." **Root cause:** The trigger required the name inline; without it the router treated the turn as ambiguous instead of locking the lifecycle command. **Fix:** The gate makes the trigger a one-way door — once fired, the only remaining question is the name. **Rule it produced:** [workspace-manager] "MUST-language gate — new-project lifecycle".

## Bug #82 — silent-task registration miss (v3.18.2; generalized Phase 3 / SPEC-2.3)
**Symptom:** Every pre-v3.17.0 upgrader silently never got the Sunday cleanup task — and the same gap re-opened for each silent background task (reconcile-sent, monthly-report, weekly-insights) as it shipped. The v3.18.1 re-run reported "all current" and exited without registering them. **Root cause:** The idempotency checks iterate `ORCHESTRATOR_MAP` (the chats); the silent tasks are intentionally not in that map and registered via a separate step — so on an existing workspace with all chats present, the skill early-exited to the management flow and the silent-task step was never reached. Pre-registry, each silent task also had its own hand-written prose block, and each block was a place to forget one. **Fix:** An unconditional Phase 5.9 assertion loops the `SILENT_TASKS` registry on EVERY invocation before any early-exit, registering whatever is missing. **Rule it produced:** [enable-command-room-schedules] "Phase 5.9 — Silent-task registration assertion".

## Session-22 Bug #11 — resolver bypass by substring grep (v3.13.7)
**Symptom:** Queries with misspelled or aliased names produced 4 clarifying questions per name for new customers, despite a shipped fuzzy resolver. **Root cause:** `entity_resolve.py` shipped v3.13.0 + hardened v3.13.6, but a live-trace showed ZERO of its three stated consumers (workspace-manager, people-crm, transcript-search) actually invoked it — the LLM substituted substring grep under time pressure. Queries worked "by luck of grep" on M's matured alias graph; new customers with empty graphs hit the failure from Day 1. **Fix:** MUST-language enforcement gate — resolver first, grep only as fallback when the resolver returns nothing. **Rule it produced:** [workspace-manager] "MUST-language enforcement gate (canonical resolver dispatch)".

## Routing-miss — "my conversation with Elon" (2026-05-20, v3.13.1)
**Symptom:** Asked 4 open-ended clarifying questions for "my conversation with Elon" when Elan was a known person the resolver would have matched. **Root cause:** Ambiguity handling fired before the substrate check, and its shape was unconstrained (multiple open-ended questions). **Fix:** Strict one-question shape with concrete options; never fall to ambiguity handling when the resolver returns a candidate. **Rule it produced:** [workspace-manager] "Step 5 — Ambiguity handling (strict shape)" + step-3 candidate rule.

## Overlay bug class — stale tracker projections (v3.11.1 morning-brief; v3.11.4 workspace-manager)
**Symptom:** The 2026-05-20 morning-brief bug report: Command Room Plugin and Desktop App threads both had events that day, but the digest reported them "quiet since April 25" / "Last touched May 8". **Root cause:** MASTER_TRACKER.md is a regenerated projection of `entities.json` + `events.jsonl`, not the source. A workspace that hasn't regenerated the tracker for 10 days reports a thread "quiet" when it has activity today. **Fix:** Every surface that renders `Last touched` / `Next Action` / `Waiting On` overlays events.jsonl newer than the tracker's `<!-- generated-at -->` stamp before rendering. The accepts on the next-day re-fire: (a) "Last touched" reflects the most recent event in events.jsonl, not the tracker snapshot's stamp; (b) any thread the tracker lists as "Waiting On" that events.jsonl shows answered gets dropped from the overdue list. **Rule it produced:** [morning-briefing] Step 3a overlay; [workspace-manager] Step 1a overlay + `go [name]` loading-sequence step 4.

## v3.11.5 — _people/ drift (PERSON.md commitment tables lag)
**Symptom:** A commitment closed via meeting-notes Step 5e-bis still showed as open in PERSON.md until workspace-manager re-rendered, and morning-brief surfaced it as overdue against the team member. **Root cause:** Team overdue/dormancy counts were read from the PERSON.md commitment table — a Tier 2 projection that lags — instead of from events.jsonl. **Fix:** Counts derive from `load_open_commitments` over events.jsonl; PERSON.md stays fine for static profile context only. **Rule it produced:** [morning-briefing] Step 3 team-derivation procedure (v3.11.5 canonical-source rule).

## Bug #98 (v1–v3) — the brief cannot be its own reconciler (v3.18.9 → v3.18.12)
**Symptom:** The morning brief kept telling the CEO to redo follow-ups they had already sent from Gmail. Three attempts to make the brief reconcile sent mail (v3.18.9 standalone step, v3.18.11 folded onto the fetch, v3.18.11 inbox-triage backstop) were ALL skipped in real use. **Root cause:** The brief diagnosed the cause itself: every step it reliably runs feeds the *visible* brief, but reconciliation's product is an *invisible* substrate write — so under pressure to ship a readable brief, the invisible-payoff step gets degraded every time. A structural incentive problem, not a willpower one; co-locating an invisible write with a visible deliverable always loses (and created a read-after-own-write hazard: closing commitments and rendering them in the same fire). The v3.18.9 receipt gate WAS gamed — the matcher was fed curated data and a truthful-sounding line was printed. **Fix (v3.18.12, Bug #98-v3):** Reconciliation moved to its own single-purpose silent task (`reconcile-sent`, 6:45 AM, before the brief) where it IS the job; the brief only READS what that task wrote. Enforcement is on the EVENT, not a narration: success is a `sent_reconcile` audit event a validator reads back (a cursor delta backed by a scan count can't be faked the way a sentence can), and the brief can't fake "closed N" either — it reads real `commitment_resolved` events or has nothing to report. The deterministic `reconcile_stale` soften floor held across all three earlier failures and remains the brief's protection when the task doesn't fire. **Rule it produced:** [morning-briefing] Step 3a-bis (reader-not-reconciler + soften floor); [reconcile-sent] the whole skill.

## v2.14.24 — pinned-body drift → the bootloader pattern
**Symptom:** Customers who never re-ran `set up command room schedules` after upgrading kept firing stale prompts; multiple early users hit it. **Root cause:** v2.14.21's fix pinned the FULL orchestrator body (~366 lines per task) into Cowork's scheduled-tasks DB, so every plugin upgrade that changed orchestrator content required a manual re-registration. **Fix:** Registration pins a tiny ~50-line bootloader that resolves the plugin root at fire time and reads the orchestrator fresh from disk — plugin upgrades propagate automatically; drift is structurally impossible. The improvisation risk didn't go away, so Phase 3.5 verifies the registered prompt has the canonical markers, correct substitutions, no frontmatter, and reasonable size. **Rule it produced:** [enable-command-room-schedules] "Per-task processing (v2.14.24+ — bootloader pattern)" + Phase 3.5.

## Phase 3 / P0.2 — hardcoded size ranges failed every healthy install
**Symptom:** Every HEALTHY install reported "Couldn't finish setting up". **Root cause:** The old Phase 3.5 gate hardcoded three mutually inconsistent size ranges (1500–3500, ~5500, abort >7000) while the real composed bootloader had grown past them. **Fix:** Bounds computed at run time from THIS run's composed bootloader (0.9×–1.5×); `tests/run_bootloader_size_gate_test.py` keeps gate and template from drifting again. **Rule it produced:** [enable-command-room-schedules] Phase 3.5 check 5.

## Phase 3 / P0.3 — verify-mode classified every healthy install "unknown / very old"
**Symptom:** `verify command room prompts` reported healthy installs as unknown/very old. **Root cause:** The old flow scanned registered prompts for `OUTPUT CONTRACT (v2.13.0+` — a marker that hasn't lived in registered prompts since the v2.14.24 bootloader model (the contract lives in the on-disk orchestrator files the bootloader reads at fire time) — and filtered on the retired `cr-*` taskId prefix (matches zero tasks on a current install). **Fix:** Verification checks each layer where that layer actually lives (bootloader markers + version stamp in the prompt; OUTPUT CONTRACT in the on-disk orchestrator files). **Rule it produced:** [enable-command-room-schedules] "Verify-only mode" checks 1–6.

## Pre-FIX1 — hand-maintained explainer times drifted from real crons
**Symptom:** The Phase 0.5 explainer copy hardcoded wrong times — `past-meetings` "9 AM" vs real 5 PM, `upcoming-meetings` "5 PM" vs real 6:30 AM. **Root cause:** The bullet list was maintained by hand, separate from `DEFAULT_SCHEDULES`. **Fix:** Render fire-times from `load_schedule_config()` at speak time so copy and registered cron can never disagree. **Rule it produced:** [enable-command-room-schedules] Phase 0.5 render-from-config rule.

## W2 — the silent-task authorization ghost class
**Symptom:** The pre-Phase-3 install ritual said "5 manual permission grants" while 9 tasks registered — the 4 silent ones sat unauthorized forever: permanent reconcile softening, frozen views, no monthly report, with no symptom the customer could see. **Root cause:** Hardcoded ritual copy drifted from the actual registration set, and a silent task that never clears Cowork's one-time Run Now permission never fires. **Fix:** Render the ritual list from what THIS RUN actually registered (including every silent task, each with its reason); the task watchdog reports `never_authorized` when a registered task has no receipt within 3 weekdays. **Rule it produced:** [enable-command-room-schedules] Phase 5 (W2) + "Authorization follow-through".

**Story:** v2.10.2 renamed 4 of the 6 daily tasks for executive clarity (`cr-meetings-today` → `cr-upcoming-meetings` "Upcoming Meetings"; `cr-inbox-pulse` → `cr-inbox` "Inbox"; `cr-cracks-watch` → `cr-dont-forget` "Pulse"; `cr-meetings-processed` → `cr-past-meetings` "Past Meetings"), merged the two commitment tasks (`cr-commitment-nudge` + `cr-commitment-chase`) into a single `cr-commitments` ("Commitments", both directions in one thread with global numbering), added the one-shot `cr-historical-backfill-N` chunk tasks for onboarding Phase 1.5, and moved the universal chat-output rules to `references/SHARED_CHAT_OUTPUT_PROTOCOL.md`. v2.14.27 later dropped the `cr-` prefix entirely (it rendered as "Cr inbox" in sidebar titles).
