# The scheduler discovery step (SCHEDDISCOVER1)

Generated by `scripts/dev/propagate_scheduler_discovery.py` from
`schedule_backend.discovery_step()`. **Do not edit by hand** — guard G75
re-renders the block and compares every copy byte for byte.

**Why it exists.** A scheduling skill decides "is there a scheduler here?" from
the tool list the model can see. On current app versions a connector's tools
arrive as names that must be LOADED through the host's tool search before they
are on that list, so a chat that looks before it loads can tell a customer
there is no scheduler on a seat that has one. The step makes the model load
first, look second, say where the chats run, and — when there really is
nothing — say why in one plain sentence.

**Where it lives.** Verbatim, between the two sentinels, in the four skills
that plan scheduler calls: `enable-command-room-schedules`, `change-schedule`,
`system-health` and `command-room-update-bridge` (above its first scheduler
use, the staff-meeting cadence migration). Its step 3 is the ONE rendered call
each skill pastes — `schedule_backend:opening_lines` through the access
layer's `run_helper` — and what that call returns is the only thing the skill
says about where the chats run or why there are none.

**Honest limit.** Whether a given session loads a waiting tool on request is
the host's behaviour. The step makes the model ASK before concluding, and the
cause line makes a "no" specific; the desktop-app triage (app version, the
app's scheduling settings, the per-machine preference, the app's own log
lines) stays an operator procedure.
