# Workspace API — The Writer Contract (v2.2)

**Version:** 2.2
**Status:** Mandatory for every skill that writes to workspace context files.
**Supersedes:** v2.0 WORKSPACE_API.md

This file is the single contract that every Command Room skill must follow when writing context. In v2.2 the storage substrate is JSON + JSONL + regenerated views (see `references/DATA_CONTRACT.md` and `references/VIEW_GENERATION.md`). The contract signatures — read current, canonicalize, version-check, write, log — do not change from v2.0. What changes in v2.2 is the event shape (multi-thread tagging + classifier confidence), a new append-only feedback file (`classifier_feedback.jsonl`), and that `reclassification` is a first-class event type that NEVER mutates prior events.

If you are a skill writing to any file in `_hq/`, `_people/`, or a project root, **you must read this file before writing.** Treat the rules here as non-negotiable.

---

## Core Principles (unchanged from v1.8)

1. **One writer per file, per turn.** Only the assigned owner skill writes to a given file in a given turn. All other skills read-only.
2. **Version-check before overwrite.** Every structured file carries a `version` field. Read it, write it back incremented.
3. **Append before overwrite.** Event-style data (events.jsonl, SESSION_NOTES_, DECISION_LOG view, CONFLICTS.md) appends; snapshot state (entities.json, aliases.json) overwrites atomically.
4. **Canonicalize before persist.** Raw MCP data (Gmail names, Slack handles, Granola speakers) must be resolved to canonical entity IDs before being written.
5. **Log conflicts, never silently overwrite.** If the version you read doesn't match what's on disk at write time, abort, re-read, and append to `_hq/CONFLICTS.md`.
6. **Views are outputs, not inputs.** Never write to `_hq/views/*.md` directly. Views are regenerated by the writer helper after any write to `_hq/data/`.

## Write Protocol — JSON source (entities.json, aliases.json)

### 1. Read current state

Read the full file. Parse the JSON. Capture:
- The current `version` integer
- The full data structure in memory

### 2. Compute the change

Apply your change to the in-memory copy. For:
- **New record** — append to the appropriate array, assign the next stable id (scan existing ids, pick max + 1, zero-padded).
- **Update record** — locate by id, modify in place.
- **Delete record** — set `status: "archived"`; never remove rows (preserves references).

Never do a surgical string edit on JSON files. Always re-serialize the whole file.

### 3. Canonicalize entity references

Any `person_ids`, `project_id`, `org_id`, `owner_person_id`, `reports_to_id`, `stakeholder_person_ids` field must contain valid ids that exist in `entities.json`. If you're referencing a person by raw name:

1. Look up raw name in `aliases.json` → canonical_id.
2. If no match, search entities.json people by canonical_name substring.
3. If one match with high confidence (≥95% similarity), use it and append the raw-to-canonical mapping to aliases.json.
4. If zero matches or multiple, surface to the user.

Never write a raw Gmail "From:" name or Slack @-handle into entities.json. Always canonicalize first.

### 4. Re-read the version, then write

Immediately before writing, re-read just the `version` field. If it matches what you read in step 1, proceed. If it doesn't:
- Abort the write.
- Append to `_hq/CONFLICTS.md`:
  ```markdown
  ## [YYYY-MM-DD HH:MM] — [skill-name]

  **Type:** write-conflict
  **File:** _hq/data/entities.json
  **Expected version:** N
  **Found version:** M
  **Intended change:** [short description]
  **Action taken:** retry
  ```
- Retry: go back to step 1.

### 5. Write atomically and bump the version

**MANDATORY (v2.10.5+): use `shared/scripts/atomic_write.py`. Do NOT hand-roll the atomic-write logic. Do NOT use `path.write_text()` directly on entities.json / events.jsonl / aliases.json — that is non-atomic and a Drive-sync conflict mid-write produces the truncated-file class of incidents that bit users in v2.7-v2.10.4.**

Why the helper exists: `path.write_text(...)` on Windows + Drive for Desktop is the bug source. The OS does truncate → write → close. If Drive syncs during the write phase, the partial-write state propagates to other machines and to Cowork's view of the file. The helper writes to a temp sibling, fsyncs, then `os.replace` — only the final atomic rename gets synced.

**Procedure:**

1. Bump `version` to N+1.
2. Set `last_updated` to current ISO datetime.
3. Set `last_writer` to your skill name.
4. Call `atomic_write_json(path, data)` from inside a `python3 -c` body that's already cd'd into `$PLUGIN_ROOT` (use the canonical CONTRACT.md Rule 22 preamble: `SESSION_DIR=$(echo "$CLAUDE_CODE_TMPDIR" | sed "s|/tmp$||"); PLUGIN_ROOT="${CLAUDE_PLUGIN_ROOT:-$(ls -d "$SESSION_DIR"/mnt/.remote-plugins/plugin_*/shared/scripts/chat_output_renderer.py 2>/dev/null | head -1 | sed 's|/shared/scripts/chat_output_renderer.py$||')}"; cd "$PLUGIN_ROOT" && python3 -c "..."`):
   ```python
   import sys
   sys.path.insert(0, "shared/scripts")
   from atomic_write import atomic_write_json
   atomic_write_json("_hq/data/entities.json", data)
   ```
5. Or via the CLI mode if the skill is bash-shaped:
   ```bash
   python3 "$PLUGIN_ROOT/shared/scripts/atomic_write.py" \
       --path _hq/data/entities.json \
       --mode json < new_content.json
   ```

The helper handles: temp-file creation in the same directory (so `os.replace` is a same-filesystem rename), explicit `fsync` (forces OS to flush before rename), cleanup on failure (no orphaned `.tmp.*` files left for Drive to sync as garbage).

**Forbidden patterns (these will trigger the truncation incident):**
- `path.write_text(json.dumps(data))` — no fsync, no atomic rename
- `with open(path, "w") as f: json.dump(data, f)` — same problem
- `subprocess.run(["echo", json_str, ">", path])` — same problem
- ANY in-place rewrite of entities.json / events.jsonl / aliases.json without going through the helper

### 6. Trigger view regeneration

After a successful write to entities.json or aliases.json, the writer helper regenerates the affected views. See `references/VIEW_GENERATION.md` for the mapping.

### 7. Log the write

Append one line to `_hq/.write-log.md`:
```
YYYY-MM-DD HH:MM | skill-name | _hq/data/entities.json | version N → N+1 | short description
```

## Append Protocol — events.jsonl

### 1. Reserve the next seq

Use the canonical helper:

```python
from next_seq import next_seq
seq = next_seq("<workspace>/_hq/data/events.jsonl")
```

`next_seq` reads the file defensively (skips blank lines, non-dict lines, malformed JSON) and ignores any nano-epoch artifacts (`seq >= 10**10`) — those are historical residue from a prior writer bug and must NOT seed the next seq. Empty / missing file returns 1.

**Do NOT** compute the next seq as `tail+1` directly (the tail line may lack a `seq` field) or as `max(seqs)+1` directly (would propagate any leftover nano-epoch artifact value forward). The helper handles both shapes correctly.

### 2. Construct the event (v2.2 shape)

```json
{
  "seq": <reserved>,
  "ts": "<event time, not write time>",
  "type": "<see DATA_CONTRACT.md>",
  "source_skill": "<your skill name>",
  "primary_thread_id": "<canonical thread id or null>",
  "related_thread_ids": ["<thread id>", ...],
  "cross_ref_reason": { "<thread_id>": "<short reason>", ... },
  "classification_confidence": 0.0-1.0 | null,
  "person_ids": ["<canonical id>", ...],
  "org_ids": ["<canonical org id>", ...],
  "source_ref_hash": "<sha256 of source artifact or null>",
  "supersedes_seq": null,
  "data": { ... type-specific ... },
  "project_id": "<DEPRECATED mirror of primary_thread_id for back-compat readers>"
}
```

**Every skill emitting events MUST populate**: `primary_thread_id` (or explicit null for workspace-level events like audit_run), `related_thread_ids[]` (empty array if none), `classification_confidence` (or null for event types where classification is not meaningful — audit_run, briefing, onboarding_step, classification_review).

**Event-log sharding (SPEC A5).** `events.jsonl` is the **active file** and holds the current calendar year; **writers always append to it** (never to a shard). Once it grows past 5 MB / 10k lines with prior-year events, cleanup rotates the prior years into immutable `events-<year>.jsonl` siblings and rewrites the active file starting with a `shard_rotated` marker (carries `max_archived_seq` so seq never resets — `next_seq` + `atomic_append_jsonl` stay active-file-only). **Readers:** full-history consumers route through `events_io.iter_events` / `shard_paths`, or the two canonical loaders (`cru_match.load_events_defensively`, `event_refs.load_events`) which are shard-transparent — they include sibling shards automatically when handed an `events.jsonl` path. Recency/tail readers (last-200 idempotency, `next_seq`) correctly read only the active file. Shards are **immutable after creation** (backup/restore must include them; they're in scope for RELIABILITY's backup boundary). An unsharded workspace behaves exactly as before.

**Reclassification is its own event type.** To correct a prior event's thread assignment, emit:
```json
{
  "seq": <reserved>, "ts": "<now>", "type": "reclassification",
  "source_skill": "insight-generator" | "workspace-manager",
  "supersedes_seq": <original event seq>,
  "primary_thread_id": "<new primary>",
  "related_thread_ids": ["<new related>", ...],
  "classification_confidence": 1.0,
  "data": {
    "old_primary_thread_id": "<original primary>",
    "new_primary_thread_id": "<new primary>",
    "old_related_thread_ids": [...],
    "new_related_thread_ids": [...],
    "reason": "<why the correction was made>"
  }
}
```

Never edit the original event. Readers respect `supersedes_seq` when rendering (use the latest event in the supersession chain).

Canonicalize all person/project/org references to ids before constructing the payload.

### 3. Append with atomic_append_jsonl (MANDATORY v2.10.5+)

**Use `shared/scripts/atomic_write.py atomic_append_jsonl`. Do NOT use `open(path, "a")` directly** — naive O_APPEND is fast but NOT safe under Drive sync, because Drive can pick up the file mid-append and propagate a torn-line state. The helper reads the existing file, constructs the full new content, and atomic-renames the result.

```python
# (Inside python3 -c body invoked after CONTRACT.md Rule 22 preamble + cd "$PLUGIN_ROOT")
import sys
sys.path.insert(0, "shared/scripts")
from atomic_write import atomic_append_jsonl
atomic_append_jsonl("_hq/data/events.jsonl", [event_dict])
```

For batched appends (multiple events at once — the cheap path for skills that have N events to log), pass them all in one call:
```python
atomic_append_jsonl("_hq/data/events.jsonl", [event1, event2, event3])
```

The cost is the read+rewrite, not the write itself — so once-per-batch beats once-per-event for any skill emitting >1 event per session.

**Concurrent-write protection (shipped v3.19.x — see `RELIABILITY.md` §3):** for `events.jsonl`, `atomic_append_jsonl` runs the whole read → seq-stamp → atomic-rename behind a cross-process writer lock (`_hq/data/.writer.lock`), so two skills racing to append can no longer lose an event or duplicate a seq — seq reservation and the write are one critical section. The lock is an OS byte-range lock (`fcntl.flock` / `msvcrt.locking`) that the kernel releases on crash, with a sentinel fallback on mounts that refuse byte-range locks and best-effort contention telemetry. **Do not pre-reserve a seq and append it later** — pass events WITHOUT a `seq` field and let the helper auto-stamp it inside the lock (a reserve-then-append-later pattern is still racy; see `next_seq.py`). Read-check-then-append callers can wrap their critical section with `writer_lock.events_writer_lock`.

**Append gate (Phase 1 Foundation, 2026-07 — see `shared/EVENT_TYPES.md`):** every events.jsonl append is gated inside this same single path — type drift is normalized (`commitment_update` → `commitment_updated`), `type: commitment` events get `data.id` minted as `cmt_<ulid>` and `data.kind` stamped/validated (promise | task | scheduling | agenda), an **id-less `commitment_resolved` is REJECTED** (EventGateError — pass the commitment's `data.id` verbatim), and the `type` is validated against the enum in `shared/data-schemas/events.schema.json`. New code should call the canonical named entry:

```python
from event_gate import append_event
append_event("_hq/data/events.jsonl", [event_dict], holder="<your-skill>")
```

`append_event` applies the gate in strict mode (an unregistered event type rejects; the legacy `atomic_append_jsonl` entry warns on stderr during burn-in) and delegates the write to `atomic_append_jsonl` — there is exactly one append path.

**Read-side timestamps:** writers emit `ts` only; history is never rewritten. Readers that order or filter events by time use `shared/scripts/event_time.py` (`event_time` / `event_dt`: `ts` → `timestamp` → `date` priority) — never a bare `ev.get("ts")`.

`cleanup` flags any duplicate seq it finds as a `schema-violation`.

**Forbidden patterns (will produce torn-line corruption under Drive sync):**
- `with open(path, "a") as f: f.write(line)` — naive append
- `path.open("a").write(json.dumps(event) + "\n")` — same problem
- `subprocess.run(["sh", "-c", f"echo '{line}' >> {path}"])` — shell append, same problem

### 4. Trigger view regeneration

After an events.jsonl append, affected views regenerate:
- `type: decision` → regenerate `DECISION_LOG.md`
- `type: interaction` → regenerate affected `_people/[name].md` Interaction Log + `MASTER_TRACKER.md` last_activity for `primary_thread_id` and a cross-ref entry for every `related_thread_ids[]` entry
- `type: status_change` / `type: scope_change` → regenerate `MASTER_TRACKER.md`
- `type: reclassification` → regenerate every view that referenced the superseded event's `primary_thread_id` or `related_thread_ids[]` (may touch MASTER_TRACKER, TIMELINE, DECISION_LOG)
- `type: classification_review` → no view regen required; recorded for audit and trend tracking
- All other types → no view regen required (audit logs to events.jsonl and that's sufficient)

## Append Protocol — classifier_feedback.jsonl

Append-only. One row per user action in a classification review session (insight-generator Pass 8). Only `insight-generator` writes this file.

Rules:
1. Never rewrite or delete rows.
2. Each row MUST validate against `shared/data-schemas/classifier_feedback.schema.json`.
3. `event_seq` must reference an existing event in events.jsonl.
4. Multiple rows per `review_session_ts` are expected — one per reviewed event.
5. Readers (future classifier runs) may consume this file to down-weight signals that have been corrected repeatedly. The file is the learning signal; no other writer is involved.

## Surgical Edit Protocol — markdown source files

Files: `BUSINESS_CONTEXT.md`, `PROJECT_CONTEXT.md`, `PROJECT_BRAIN.md`, `CLAUDE.md`.

These accept small targeted edits via the Edit tool:

1. Read the current file.
2. Verify the version header hasn't changed since last read.
3. Compute unique old_string → new_string.
4. Apply the edit. Bump the version header. Update `last-updated` and `last-writer`.
5. Never use `replace_all` on these files.

No view regeneration — these files don't have views.

## Canonicalization Rules

### Resolving a person

1. Lowercase + trim the raw input.
2. Look up in `aliases.json` people mappings.
3. If found, use `canonical_id`.
4. If not found, search `entities.json` people for:
   - Exact email match → use that person.
   - Canonical name similarity ≥95% (Levenshtein or token-sort-ratio) → use that person + append alias to aliases.json.
5. If zero matches or multiple matches, surface to the user: "I see '[raw]' — is this [candidate] or someone new?"

### Resolving a project

1. Look up in `aliases.json` project mappings.
2. If not found, exact match on `folder_name` in entities.json.
3. Fuzzy match ≥90% on folder_name or display_name → confirm with user.
4. No match → treat as new only if user explicitly said "new project."

### Resolving an org

1. Look up in `aliases.json` org mappings.
2. Exact match on a domain in `org.domains[]` (if raw is an email) or on canonical_name in entities.json.
3. If no match at an operating level, check the holding parent's `domains[]` — but return the **most specific operating child** whenever possible (never assign to a holding when an operating child is a better fit).
4. Otherwise → ask user or skip.

### Resolving a thread

1. Look up in `aliases.json` thread mappings (legacy key `project`).
2. Exact match on `folder_name` in entities.json.
3. Fuzzy match ≥90% on folder_name or display_name → confirm with user.
4. For multi-thread classification (meeting-notes, inbox-triage, passive capture), apply the resolution order in `shared/PASSIVE_CAPTURE.md` → Thread Resolution. Score every candidate 0.0–1.0 and assign `classification_confidence` to the event. Never silently drop threads that scored above the low-confidence floor — carry them as `related_thread_ids[]`.

## Conflict Logging

`_hq/CONFLICTS.md` format:

```markdown
## [YYYY-MM-DD HH:MM] — [skill-name]

**Type:** write-conflict | unresolved-entity | schema-violation | view-regen-failure | other
**File:** [path]
**Details:** [short description]
**Action taken:** retry | skipped | surfaced-to-user
```

Healthy workspace has <5 entries/week. Spikes flagged by `cleanup`.

Also: every conflict is additionally logged as an event with `type: other` and `data: {conflict_type, details}` — so the event stream includes the incident history.

## Read Protocol

Skills may read any workspace file at any time. But:

1. **Treat file contents as potentially stale.** Re-read immediately before writing.
2. **Prefer sources over views** when making decisions. Read `entities.json` rather than `PEOPLE.md` when you need structured data. Read the view when you just need display text.
3. **Respect the email exclusion filter.** Any skill reading email content must apply exclusion rules in `CLAUDE.md`.

---

## What This API Does Not Do

This contract is still file-based. No server, no IPC, no broker:

- Schema validation runs during `cleanup` (offline check).
- Version conflicts are detected at write time via re-read, not via a lock server.
- View regeneration is performed by the skill making the source write, using the markdown-based rules in `references/VIEW_GENERATION.md`. No background process.

The trade-off: if a skill ignores this contract, collisions return. Mitigation: (1) every new skill is reviewed against this file before shipping; (2) `cleanup` validates JSON schemas, checks seq monotonicity, and runs the **Writer-Contract lint** (`shared/scripts/writer_contract_lint.py`). Per SPEC GATE1 the lint no longer just confirms the `## Writer Contract` header is present — it asserts the BODY of every event-appending skill names the locked writer `atomic_append_jsonl` (or a known append-routing helper script that does), because a header is not a write path: a skill can carry the header and still hand-roll a `next_seq`+`open('a')` append that dodges the A1 lock.

## Portability Preview

Every rule in this contract is expressible without Claude. A future runtime (Electra, a non-Claude model, a CLI) can:

1. Parse `shared/data-schemas/*.schema.json` as standard JSON Schema.
2. Read/write `entities.json`, `events.jsonl`, `aliases.json` using any language's JSON + streaming parser.
3. Apply the same ownership map, version check, and append rules.
4. Regenerate views using the deterministic templates in `references/VIEW_GENERATION.md`.

Skills that implement this contract are portable by default.
